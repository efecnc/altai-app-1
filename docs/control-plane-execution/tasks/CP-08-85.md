## Outcome

`altai-cli paperclip-spike --plane real` runs the CP-08-84 scenario over
**real HTTP**: the same production `router_with_control_repositories`
wiring, bound to a loopback listener (`axum::serve`), with every step a
genuine wire round trip through a hyper client riding the same stack the
daemon serves with — no new external crates.

New phases beyond the 084 rehearsal, each with its own typed exit code:

- **attempt (36):** the scheduler-internal attempt record
  (Created → Claimed → Dispatched → Running, the path the finalizer
  builds on), `POST /v1/runtime/run-bindings` binding the run to the
  attempt (052), the scripted IsanAgent lifecycle — the production
  `map_lifecycle_to_event` translation of a deterministic
  `Started`/`Terminated{Completed}` pair, no model called — ingested
  through the plane's own activity repository (ingestion has no wire
  route by design), and `POST /v1/runtime/attempts/{id}/finalize`
  reporting run completion as the verification signal (034).
- **events (37):** the downstream observes the translated run events
  through the framed query wire — `POST /v1/protocol/commands` with a
  `query_activity` envelope filtered to the Work item, asserting the
  translated pair is visible by `correlation_id` (035).
- **review (38):** the downstream Paperclip plane's projection of the
  spike Work reaches **Review with evidence** (045) — polled through
  Paperclip's existing issue API
  (`GET {downstream}/api/issues/{issue}`), asserting `in_review`
  **and** a non-empty `workProducts` list. No downstream route is
  added for the spike; the plane runs in its default `local_trusted`
  mode (localhost only, charter §2.8) where the issue API answers the
  implicit board actor.

The review phase first runs the **downstream lane** — the real
cross-repo exercise: both sides derive the lane's Work item id from
the Paperclip issue id (`wi_paperclip_<slug>`); the downstream's
`altai-host` adapter dispatches into that lane (negotiate, register,
enqueue wake over the wire), the harness waits for the wake by
claiming over the wire (404 until dispatched), then executes the lane
as the plan's topology names — transactional checkout, the
scheduler-internal attempt lifecycle, the scripted IsanAgent run's
translated events, and finalization — which the adapter observes
through the framed query wire and resolves into Paperclip's run
result. The projection the review probe then asserts is driven by
Paperclip's own orchestrator, not by the harness.

CLI contract for the 080 acceptance run:

```
altai-cli paperclip-spike --plane real \
  [--bind 127.0.0.1:PORT] \        # the port the altai-host adapter targets
  --bootstrap-token <local-bootstrap-token> \ # or PAPERCLIP_SPIKE_BOOTSTRAP_TOKEN
  --downstream-url http://127.0.0.1:3000 \   # or PAPERCLIP_SPIKE_DOWNSTREAM_URL
  --downstream-issue <issue-id>               # or PAPERCLIP_SPIKE_DOWNSTREAM_ISSUE
```

The two downstream flags must be set together. Without them the review
phase records a typed skip — CI keeps exercising attempt/events over
real HTTP with no Paperclip service, exactly as plan §3 requires.
For an actual downstream acceptance run, provide a local bootstrap token and
configure the adapter with the same value. The harness otherwise generates a
token privately for its self-contained rehearsal and never writes it to output.
